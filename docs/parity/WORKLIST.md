# Parity worklist

The single build plan for closing mobile → web parity. It is the merge of the nine
independently-triaged area worklists in this directory, deduplicated, dependency-ordered,
and stripped of everything that is not a real capability gap.

**Read this instead of the nine area docs.** Those remain as the evidence trail — every
item below cites the file and line that proves it — but they disagree with each other in
places, over-count in others, and were ranked by a severity model that no longer applies.
Where they conflicted, [Triage notes carried forward](#triage-notes-carried-forward)
records the call.

## What counts as a gap

Per the product owner, and overriding any severity or wording in the source docs:

> A **GAP** is a feature or capability a MOBILE user has that a WEB user does not.

Explicitly **not** gaps — do not carry these forward, do not re-open them:

- A mobile full screen rendered as a modal / sheet / inline panel / new tab on web.
- Mobile's separate pages collapsed into tabs, or vice versa.
- Any navigation, layout, spacing, **ordering** or visual restructuring.
- Web using the extra screen space differently. This is wanted, not a defect.
- Copy differences that carry the same meaning.

Presentation is free. Capability is not.

Four further classifications keep settled questions settled, and all of them live in
[Not being built](#not-being-built) with evidence:

| Class | Meaning |
|---|---|
| `PRESENTATION` | Same capability, different container / copy / ordering. |
| `ALREADY_PRESENT` | The doc claimed web lacks it; web has it. A doc error. |
| `MOBILE_BUG_DONT_PORT` | Mobile is internally inconsistent or plainly wrong. The correct behaviour web should implement is stated. |
| `DEAD_CODE_DONT_PORT` | The mobile code is unreachable, so no mobile user has the capability. |
| `WEB_AHEAD_PRESERVE` | Web exceeds mobile here. Must survive the parity work — deleting it is a regression. |

## Why the old severity labels are void

**The web app is not launched.** There are no real users affected by anything in this
document. The `critical` / `high` / `medium` labels in the source docs were ranked by user
harm, which is currently zero for every row. They have been dropped and are not recoverable
from this file on purpose.

Items are ordered by **what unblocks other work**. The spine is:

1. **Correctness** — things that are wrong regardless of parity, plus the one-line enablers.
2. **Shared layers** — each landed with one real consumer so it is provably working.
3. **Area sweeps** — Chat, Groups, Buddies, Profile/Settings, Live, Auth, Updates.
4. **Cross-cutting finishers** — analytics, constants.
5. **Blocked** — backend work or a product decision we do not own.

`size` is `xs` (hours) / `s` (≈1 day) / `m` (2–4 days) / `l` (1–2 weeks) / `xl` (multi-week).

Full sub-item lists, refs, evidence and dependencies for every build item are in
`docs/parity/_triage-raw.json` and `_verify-raw.json`. Item ids are stable and will be
referenced by tickets.

### Phase 1 — Shared layers, each with one proving consumer ✅ DONE

> **Completed 2026-08-07.** All 17 items shipped; `npm test` (251 assertions),
> `tsc --noEmit`, `eslint` and `next build` green. What later phases can now rely
> on, and what was learned building it:
>
> - **A subscription filter is matched against the fields the *mutation*
>   returned**, not the stored row. `updateConnection` selected only
>   `{id, accepted}`, so `onUpdateConnection`'s `or:[remitent, recipient]` filter
>   could never match and the subscription would have been dead on arrival. All
>   three connection mutations now select both participant ids, with a test
>   pinning it. Mobile documents the same trap.
> - **The maintenance gate is deliberately narrower than mobile's.** The
>   production record read `REQUIRED_UPDATE` when this was built, so porting
>   mobile's gate verbatim would have blocked every web visitor on day one for a
>   condition that cannot apply in a browser. Only `INMAINTENANCE` blocks; every
>   other value and every error path fails open.
> - **Making an optional parameter required is a good way to find dropped work.**
>   `createPost`/`addComment`/`addReply` took `attachments?: unknown[]` that
>   nothing ever passed. Typing it as required turned three silent omissions into
>   compile errors.
> - **`Link`'s `onNavigate` is synchronous.** It cannot await a dialog, so the
>   unsaved-changes guard cancels the navigation outright and re-issues it if the
>   person chooses to leave. Browser back needs a separate history sentinel.
> - **Two composers now hold HTML, not plain text.** `openForEdit`/`serialize`
>   replace the lossy `postHtmlToText` → textarea → `textToPostHtml` round trip
>   that destroyed formatting on every web edit.
>
> Still no backend, schema or mobile-repo change. AWS access remained read-only
> introspection, used to confirm the maintenance record's current value.


**Rationale.** Every item in Phases 2–8 imports something from here, so building these
late means building each area twice. The constraint is that no layer ships alone: each is
paired with a real consumer in the same phase so it is provably working before an area

> ```
>

>   correct, and nothing reading that table can tell a browser token from a phone
>   one.
> - **The primary key is the token string**, so one token is one row. A web token
>   and a phone token are different strings from different Firebase projects and
>   can never collide. Mobile's dedupe selects `token == mine AND userID != me`
>   (`useAuth.ts:82-115`); its logout selects `token == mine AND userID == me`
>   (`:161-200`). **Neither can select a web row, and no web write can select a
>   phone row.** A unit test pins the reducer to that property.

>   tokens** (mobile never removes its own stale rows, only rows for the same
>   token under other accounts). Mobile push works today, so whatever sends it
>   already tolerates dead tokens in a member's list.
>

> it settles the last doubt: `sendMulticast` filters null/empty tokens, sends via
> `messaging().sendEach` — one independent message per token — and auto-deletes
> tokens that come back invalid. It **skips, it does not abort**. Tokens are read
> per recipient, so a web row could never reach another member, and cannot harm
> its own member's phone delivery either.
>

> project that minted them; web push runs on this app's own Firebase project while
> the sender holds the *mobile* project's credentials, so a registered web token

> the auto-removal list, so the row would linger and fail forever. Zero pushes
> gained, one permanently failing row added.
